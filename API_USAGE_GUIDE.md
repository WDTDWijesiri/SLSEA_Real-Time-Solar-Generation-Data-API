# API Authentication and cURL Usage Guide

This guide demonstrates authentication and authenticated requests against the deployed Real-Time-Solar-Generation-Data-API.

## Deployment URLs

```text
API base URL: https://real-time-solar-generation-data-api-zeta.vercel.app
Swagger UI:   https://real-time-solar-generation-data-api-zeta.vercel.app/docs/
Health check: https://real-time-solar-generation-data-api-zeta.vercel.app/health
```

Set the base URL once in the terminal:

```bash
BASE_URL="https://real-time-solar-generation-data-api-zeta.vercel.app"
```

## 1. Check API availability

```bash
curl -i "$BASE_URL/health"
```

Expected status: `200 OK`.

## 2. Obtain a user Bearer token

Request a national user token:

```bash
curl -sS -X POST "$BASE_URL/api/v1/auth/user-token" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{
    "email": "national@slsea.gov.lk",
    "password": "NationalDemo!2026"
  }'
```

A successful response contains:

```json
{
  "accessToken": "eyJ...",
  "tokenType": "Bearer",
  "expiresIn": 3600,
  "user": {
    "role": "national"
  }
}
```

The token expires after 3,600 seconds (one hour).

### Automatically store the token with jq

Install `jq` on macOS if it is unavailable:

```bash
brew install jq
```

Obtain and store the token:

```bash
USER_TOKEN=$(curl -sS -X POST "$BASE_URL/api/v1/auth/user-token" \
  -H "Content-Type: application/json" \
  -d '{"email":"national@slsea.gov.lk","password":"NationalDemo!2026"}' \
  | jq -r '.accessToken')
```

Confirm that a token was captured without printing the secret token:

```bash
test -n "$USER_TOKEN" && echo "User token captured"
```

## 3. Make authenticated read requests

List all visible provinces:

```bash
curl -sS "$BASE_URL/api/v1/provinces" \
  -H "Authorization: Bearer $USER_TOKEN" \
  -H "Accept: application/json" | jq
```

List the districts in province `1`:

```bash
curl -sS "$BASE_URL/api/v1/provinces/1/districts" \
  -H "Authorization: Bearer $USER_TOKEN" \
  -H "Accept: application/json" | jq
```

List the substations in district `1`:

```bash
curl -sS "$BASE_URL/api/v1/districts/1/substations" \
  -H "Authorization: Bearer $USER_TOKEN" \
  -H "Accept: application/json" | jq
```

Retrieve installation `1`:

```bash
curl -sS "$BASE_URL/api/v1/installations/1" \
  -H "Authorization: Bearer $USER_TOKEN" \
  -H "Accept: application/json" | jq
```

Retrieve its latest reading:

```bash
curl -sS "$BASE_URL/api/v1/installations/1/latest-reading" \
  -H "Authorization: Bearer $USER_TOKEN" \
  -H "Accept: application/json" | jq
```

Retrieve a paginated reading history:

```bash
curl -sS "$BASE_URL/api/v1/installations/1/readings?page=1&pageSize=5&sort=-recordedAt" \
  -H "Authorization: Bearer $USER_TOKEN" \
  -H "Accept: application/json" | jq
```

Search readings across the permitted jurisdiction:

```bash
curl -sS "$BASE_URL/api/v1/readings?page=1&pageSize=10&provinceId=1&sort=-recordedAt" \
  -H "Authorization: Bearer $USER_TOKEN" \
  -H "Accept: application/json" | jq
```

Retrieve the district generation summary:

```bash
curl -sS "$BASE_URL/api/v1/districts/1/generation-summary" \
  -H "Authorization: Bearer $USER_TOKEN" \
  -H "Accept: application/json" | jq
```

## 4. Demonstrate jurisdiction-scoped access

Obtain a Colombo District token:

```bash
DISTRICT_TOKEN=$(curl -sS -X POST "$BASE_URL/api/v1/auth/user-token" \
  -H "Content-Type: application/json" \
  -d '{"email":"col@slsea.gov.lk","password":"NationalDemo!2026"}' \
  | jq -r '.accessToken')
```

Use it like any Bearer token:

```bash
curl -sS "$BASE_URL/api/v1/provinces" \
  -H "Authorization: Bearer $DISTRICT_TOKEN" \
  -H "Accept: application/json" | jq
```

The response is restricted to the district user's permitted jurisdiction. Out-of-scope resource identifiers return `404` to avoid disclosing their existence.

## 5. Obtain a device Bearer token

Device tokens are separate from user tokens. They authorize reading ingestion for exactly one installation.

```bash
DEVICE_LOGIN=$(curl -sS -X POST "$BASE_URL/api/v1/auth/device-token" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{
    "meterId": "SL-MTR-00001",
    "secret": "MeterDemo!2026"
  }')

DEVICE_TOKEN=$(printf '%s' "$DEVICE_LOGIN" | jq -r '.accessToken')
INSTALLATION_ID=$(printf '%s' "$DEVICE_LOGIN" | jq -r '.installationId')
```

Confirm the values without printing the token:

```bash
test -n "$DEVICE_TOKEN" && echo "Device token captured for installation $INSTALLATION_ID"
```

## 6. Insert a generation reading

Generate a current UTC timestamp:

```bash
RECORDED_AT=$(date -u +"%Y-%m-%dT%H:%M:%S.000Z")
```

Post a reading using the device token:

```bash
curl -i -X POST "$BASE_URL/api/v1/installations/$INSTALLATION_ID/readings" \
  -H "Authorization: Bearer $DEVICE_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d "{
    \"recordedAt\": \"$RECORDED_AT\",
    \"powerKw\": 2.75,
    \"cumulativeEnergyKwh\": 999999.25,
    \"voltageV\": 230.5
  }"
```

Expected status: `201 Created`. The response contains the new integer reading ID, and the `Location` header identifies its atomic resource URL.

Read the created resource using the user token, replacing `{readingId}` with the returned ID:

```bash
curl -sS "$BASE_URL/api/v1/readings/{readingId}" \
  -H "Authorization: Bearer $USER_TOKEN" \
  -H "Accept: application/json" | jq
```

Do not repeatedly submit the same timestamp. The API prevents duplicate readings for the same installation and timestamp.

## 7. Use a token in Swagger UI

1. Open `https://real-time-solar-generation-data-api-zeta.vercel.app/docs/`.
2. Obtain a token using the login endpoint or the cURL command above.
3. Select **Authorize** in Swagger UI.
4. Paste only the JWT value. Swagger adds the `Bearer` prefix automatically.
5. Select **Authorize**, close the dialog, and use **Try it out** on a protected operation.

Use a user token for read endpoints. Use a device token only for `POST /api/v1/installations/{installationId}/readings`.

## Common authentication errors

| Status | Meaning | Typical solution |
|---|---|---|
| `400 Bad Request` | Invalid request body or parameters | Check property names, types, timestamps, and pagination values |
| `401 Unauthorized` | Missing, invalid, or expired token | Log in again and send `Authorization: Bearer <token>` |
| `403 Forbidden` | Valid token without permission | Use the correct device installation or a user with the required scope |
| `404 Not Found` | Resource absent or outside the user's jurisdiction | Check the integer ID and the logged-in user's scope |
| `409 Conflict` | Duplicate or conflicting reading | Use a new timestamp and valid cumulative-energy value |
